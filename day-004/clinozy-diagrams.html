Clinozy: how the whole system works

Clinozy is a clinic management app. Many clinics share one system, and each clinic only sees its own data. The frontend is a React website. The backend is a Fastify API with a Postgres database, plus a worker for background jobs.

8. Login flow (email code + MFA) sequence

The main login uses an email code. Sign-up works the same way: a new email simply creates a new user. If MFA is on, there's one more step. The access token lives only in memory, and the refresh token is a secure cookie.

sequenceDiagram
  autonumber
  actor U as Staff
  participant FE as Frontend
  participant API as API /auth
  participant R as Redis
  participant DB as Postgres
  participant W as Worker → Resend
  U->>FE: type email on /login
  FE->>API: POST /email/send-code + captcha
  API->>DB: user (create if new) + verification_tokens
  API-->>W: mail_outbox → mail queue
  W-->>U: email with 6-digit code
  API-->>FE: 200 (always same answer)
  U->>FE: type code
  FE->>API: POST /email/login {email, code}
  API->>DB: mark code used · is_email_verified
  alt MFA needed (user or clinic policy)
    API->>R: mfa:session (5 min)
    API-->>FE: mfa_required + mfa_session_token
    FE->>FE: go to /mfa
    U->>FE: type TOTP / recovery code
    FE->>API: POST /mfa/login
    API->>DB: check mfa_methods
  end
  API->>DB: pick active clinic · INSERT auth.sessions
  API-->>FE: access_token (JWT, 15 min) + session_id cookie (HttpOnly)
  FE->>API: GET /me/context + GET /users/me/organizations
  FE->>FE: token in memory · refresh timer · go to /organization/$slug/today

9. Token refresh on 401 sequence

When the 15-minute token expires, the frontend quietly gets a new one and tries again. Only one refresh runs at a time, even across tabs. Each refresh secret works only once: reusing an old one logs out all of that user's sessions.

sequenceDiagram
  autonumber
  participant P as Page
  participant H as fetch-client
  participant API as API
  participant DB as Postgres
  P->>H: GET /app/patients
  H->>API: request + old Bearer token
  API-->>H: 401
  H->>H: lock (navigator.locks · one refresh for all tabs)
  H->>API: POST /auth/refresh (session_id cookie)
  API->>DB: load session · check expiry · user active
  alt refresh secret is current
    API->>DB: rotate refresh hash · new token_hash
    API-->>H: new access_token + new cookie
    H->>API: replay GET /app/patients
    API-->>H: 200 data
    H-->>P: data
  else old secret reused (stolen?)
    API->>DB: revoke whole session family
    API-->>H: 401
    H->>H: forceLogout() → tell other tabs → /login
  end

11. Book an appointment business flow

From the booking drawer to the database. The backend checks branch hours, holidays and doctor hours. Postgres itself blocks two bookings for the same doctor, room or machine at the same time.

  S->>FE: pick patient, service, doctor, time
  FE->>API: POST /appointments + idempotency key
  API->>API: auth · permission appointment:create
  API->>DB: room + machine belong to branch?

    API->>API: today, now, status = checked_in

13. Prescription → pharmacy sale → payment end-to-end

The doctor writes and approves a prescription. The pharmacy sells it: medicine is taken from the batches that expire first (FEFO), an invoice is made, and the payment is recorded if the cash day is still open. A prescription can be filled only once.

sequenceDiagram
  autonumber
  actor D as Doctor
  actor Ph as Pharmacist
  participant FE as Frontend
  participant API as API /app
  participant DB as Postgres
  D->>FE: patient file → prescriptions → New
  FE->>API: GET /prescription-kits, /medicines
  D->>FE: fill form (Zod check) → Save + approve
  FE->>API: POST /patients/{id}/prescriptions
  API->>DB: INSERT prescription (draft)
  FE->>API: POST …/prescriptions/{id}/approve
  API->>DB: status approved, approved_by
  Ph->>FE: pharmacy queue
  FE->>API: GET /patient-prescriptions
  Ph->>FE: sell + take payment
  FE->>API: POST /medical-sales {prescription, payment}
  API->>DB: prescription approved + same patient?
  loop each medicine
    API->>DB: SELECT batches not expired ORDER BY expiry FOR UPDATE
    API->>DB: lower batch quantity (FEFO)
  end
  API->>DB: INSERT invoice (type medical) + items
  API->>DB: day_closes: is today open?
  alt day open
    API->>DB: INSERT payment (cash / UPI / card) · raise paid_amount
  else day closed
    API-->>FE: 409 day_closed
  end
  API->>DB: INSERT medical_sale (unique per prescription)
  API-->>FE: 200 sale + invoice
